# 进张计算引擎需求（packages/engine）

> 对应 PRD §7（核心引擎需求）+ §8（质量约束）。引擎是 P0：判分、讲解数据、出题校验三处消费。

## 一、功能需求

### 1. 输入 / 输出

```
输入：13 或 14 张手牌（V1 无副露、无明示牌），如 ["1m","2m","3m",...,"4s"]
输出（14 张时）：
  每种可切牌 candidate：
    { discard, shantenAfter, ukeireCount, ukeireTiles[] }
  其中 ukeireCount = 切该牌后，能使向听数 -1 的进张总张数（含手牌内已占用的扣减）
  + 全局：当前向听数、按 (shantenAfter, -ukeireCount) 排序的最优切牌列表
```

- 13 张输入时输出「当前向听数 + 各摸牌后的向听数变化」（供讲解与出题模板用）
- **并列最优**：进张数相同的切法全部返回、排序不分先后；题目若存在并列，讲解必须说明（PRD A.3 #3）

### 2. 口径定义（判定标准，写死在测试里）

| 术语 | 口径 |
|---|---|
| 向听数 | 标准形（4 面子 + 1 雀头）公式：`8 − 2×面子数 − min(搭子数, 4−面子数) − 雀头`（搭子上限取 4−面子数——面子候补满 4 后多余搭子不产生进度；已由随机测试反例验证：一面子+四搭子+雀头实为 2 向听）；V1 不实现七对/国士（PRD 6.4：七对仅作题目标注，不进判定主流程） |
| 进张张数 | 剩余可摸张数 = 4 − 手中该牌张数（V1 不考虑他家可见牌、副露、宝牌指示） |
| 最优切牌 | 进张数优先；改良（好形变化）不参与 V1 判定，仅出现在 L6 题目讲解文案中（PRD 7.2） |

### 3. 性能

单题（14 张全候选枚举）≤ 10ms（桌面浏览器）；PRD 要求判分 + 讲解展示 ≤ 1s，余量全部留给 UI。

## 二、算法要点（实现提示）

- 牌编码：34 种，`m0-8 / p0-8 / s0-8 / z0-6` → 数组下标 0-33；对外字符串 `"3m"` 互转
- 向听数：经典标准形递推（面子/搭子/雀头组合枚举），每花色独立枚举后合并——教科书算法，先暴力后优化
- 进张枚举：对每种切牌（≤14 种）× 每种摸牌（34 种）重算向听数，纯暴力 ≈ 500 次向听计算/题，足够快
- 纯函数 + 无状态：同输入必同输出，天然适配 golden 测试与 React 渲染

## 三、验收与测试策略（PRD §8 的落地）

1. **golden 用例集**（`engine/tests/golden/*.json`）：
   - 教材例题手抄结论：79博客「牌效率」系列例题、Riichi Book I Ch3/Ch4 例题，逐题记录
     「手牌 → 最优切牌 + 进张数」，引擎输出必须一致
   - 边界用例：纯搭子手牌 / 字牌对子 / 多并列最优 / 已听牌 / 天听级好形
2. **第三方对拍 ≥ 20 题**：同一批手牌喂给独立实现（候选：mahjong-utils TS/Python、天凤牌效工具截图），
   比对向听数与进张张数；结果记录进 `docs/references/` 供追溯
3. **随机自洽测试**：随机生成 10⁴ 手合法牌型，断言：最优切牌切出后向听数不升、进张枚举无遗漏种类、
   14↔13 张转换一致
4. **出题校验 CLI**（`engine/bin/verify.ts`）：题库 JSON 全量跑一遍——`correct_discard` 必须落在
   引擎最优集合内（或并列说明齐全），不一致的题拒绝入库

## 四、交付形态

- `packages/engine`：ESM + 类型声明，零运行时依赖；Node ≥ 20 与浏览器双目标
- 对外 API（草案）：`parseHand() / shanten() / analyze14() / analyze13() / verifyQuestion()`
